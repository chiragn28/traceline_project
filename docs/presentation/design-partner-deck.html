The Question

Can you name every service account with access to your customer database right now?

Take five seconds

If the honest answer was "let me check a spreadsheet" — that's not a personal failing. It's the actual gap this whole deck is about.

02 / 09
Why Now

This isn't a nice-to-have. It's already the expectation.

Regional regulatory guidance — across DFSA and ADGM technology-risk frameworks — already calls for least-privilege access, prompt revocation, and recurring access reviews as a baseline control, not an aspiration.

⎔  The gap isn't the rule. It's that nobody's built the thing that actually checks it.
03 / 09
What Actually Happens

Here's what "we did an access review" usually means.

→ Export a list of everyone with access
→ Email each system owner: "do you still need this?"
→ Wait. Chase replies.
→ Paste whatever comes back into a spreadsheet
→ Screenshot it. That's the "evidence."

That's not a review. That's a paper trail for a review that didn't quite happen.

05 / 09
Before You Ask

Yes. It's read-only. Here's proof, not a promise.

✓

Read-only, verified

Checked for write access at connection time and on demand — not just assumed.

✓

No raw queries stored

Metadata only: actor, table, timestamp. The statement itself is never retained.

✓

Tenant-isolated by design

Postgres row-level security enforces isolation at the database layer, not just app code.

✓

Live grant introspection

Reads actual database permissions directly, catching dormant access a log alone would miss.

✓

Immutable decisions

A review decision, once made, is never edited — only corrected by the next cycle.

✓

Hash-stamped evidence

Every export is SHA-256 stamped and timestamped the moment it's generated.
