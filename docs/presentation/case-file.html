Who still has
access to your

SOC 2 and ISO 27001 both require a periodic access review. For every AWS account, Okta group, and GitHub repo, Vanta and Drata already answer this automatically. For the actual database sitting behind your product, the honest answer today is: nobody's checked since the spreadsheet from last quarter.

LIVE — access_event stream, public.customers
Exhibit A

The complaint

A required control, answered by hand.

Both frameworks ask the same question every quarter: does every person and service account with access to sensitive data still need it? When the answer lives in AWS or Okta, a GRC platform pulls it automatically. When it lives inside a Postgres or MySQL instance, someone exports a user list, emails each system owner, waits for replies, and pastes the result into a spreadsheet — which becomes the "evidence" an auditor is handed.

01

Dormant grants nobody remembers

A contractor's SELECT permission from a project that ended last year. Still valid. Still nobody's job to notice.

02

Service accounts with no owner

A pipeline credential shows up in the logs. Whoever set it up left the company. It reads as "system," and reviewers skip past it.

03

Evidence that's a screenshot of a spreadsheet

No hash, no timestamp, no record of who actually decided what. An auditor who pushes on it gets a shrug.

Exhibit B

The blind spot

Managed or self-hosted doesn't matter.

The moment it's a real database — RDS-managed or on your own box — the access-review control drops below the API surface every GRC integration actually reads from. Vanta's AWS connector checks the account. It has no idea who's logged into the database running inside it.

What Drata / Vanta sees
  • IAM policy attached to the instance
  • Encryption at rest, enabled
  • Automated backups, configured
  • Security group rules
What's actually inside it
  • Which database users/roles exist
  • What each one has been GRANTed
  • Who queried the customers table, and when
  • Whether that access is still needed
— THE GAP EVERY SPREADSHEET REVIEW LIVES IN —
Exhibit C

The fix

Read-only access, in. Audit-grade evidence, out.

Traceline connects to the database itself — never a proxy, never write access, verified read-only at connection time — and tails the access log the database is already writing. It classifies which tables are sensitive, flags accesses from outside an approved region, and generates one review item per (actor, table) pair.

The part a spreadsheet review structurally can't do: Traceline also queries the database's live GRANTs at review time. A permission nobody's used in 90 days still surfaces — tagged dormant grant — instead of quietly not existing in anyone's evidence.

Exhibit C — continued

The mechanism

Eight steps. No raw query text ever stored.

01

Connect

A read-only credential. Verified read-only at connection time, checked again on demand.

02

Discover tables

Schema introspection finds every table on the connected source.

03

Tag classification

pii, financial, public — append-only, so a report always reflects the tag active at the time access occurred.

04

Ingest

Tails the access log, dedupes, checkpoints. Coverage gaps are surfaced, never hidden.

05

Flag violations

Region rules run against observed access. Unknown region counts as a candidate, not a pass.

06

Run a review cycle

One item per (actor, sensitive table) pair — from observed access, live grants, or both.

07

Reviewer decides

Approve or revoke. Immutable once made — a wrong call is corrected by the next cycle, not edited.

08

Export evidence

Hash-stamped, timestamped CSV — the shape of evidence an auditor already expects to see.

Chain of custody

Why the evidence holds up.

Read-only, verified

Connection is checked for write grants at setup and on demand — not just assumed.

Row-level security

Postgres RLS enforces tenant isolation at the database itself, not only in application code.

Real grant introspection

Immutable decisions

A review decision, once made, is never edited — only corrected by the next cycle.
